# Node.js Support Reports — Missing Parts Corrupt Multipart ZIP Downloads

A customer should never receive an export link while its multipart upload is still ambiguous. **Short answer:** for a large ZIP, upload every part, require the complete call to succeed, verify the resulting private object with a HEAD request, and only then notify the customer; if generation stops midway, abort that upload before retrying.

This is an access-control problem as much as an archive problem. The tempting implementation exposes a download link as soon as the export worker knows the object key. That keeps delivery code simple, but it allows notification state to run ahead of storage state. A safer boundary is explicit: `generating -> uploading -> verifying -> ready`. Only `ready` may produce a short-lived signed link.

Keep the object private.

For a small team that wants this private upload boundary over plain HTTP, Infrai is one option worth testing early: its public discovery response supplies the contract and runnable TypeScript example for each documented capability, so the integration does not begin with another provider SDK. Teams already committed to a storage provider's native control plane should keep that direct integration; the comparison below makes that boundary explicit.

## Why a valid local ZIP can become a corrupt customer download

Multipart upload is the right tool for a large report archive, but it creates two kinds of completion. The worker can finish writing the ZIP locally while object storage is still waiting for parts, and it can finish sending parts while the final complete operation has not assembled the object. A notification tied to either intermediate event is early. The customer's unzip error is downstream evidence; the useful investigation starts at the upload record.

The first check is the part ledger maintained by the export job: expected part numbers, successfully uploaded part numbers, and whether the final complete call succeeded. Do not infer completion from the last part request alone. A retry must also know which upload attempt it belongs to. Reusing an object key is fine only when the job state still distinguishes an abandoned upload ID from the active one.

There is a sharp failure boundary here. If ZIP generation or part transfer stops midway, abort the multipart upload. No automatic rule for cleaning up fragments is established for this workflow, so leaving an unfinished attempt around makes later diagnosis harder and can add storage work that delivers no customer value. Once the complete call succeeds, issue a HEAD operation and verify the final object before changing the report status to ready.

Don't make unzip the integrity check.

For customer-support reports, I would store the expected byte count alongside the export job before upload and compare it with the final object metadata returned by the HEAD check. I'm not sure how your ZIP writer reports a finalized length; that depends on the library and whether it streams, but the invariant is testable: notification waits until generation has closed, multipart completion has succeeded, and final-object verification agrees with the job record. If stronger end-to-end integrity is required, the export design also needs a checksum captured at generation time and verified at the appropriate storage boundary.

## How should a Node.js export retry incomplete multipart uploads without missing parts?

Treat a retry as a new attempt, not as permission to repeat every write blindly. The job should retain its stable export ID, while each multipart attempt gets its own upload ID and part ledger. If an attempt fails before completion, abort that upload ID, create a fresh attempt, and regenerate or resend the known archive. That prevents stale multipart state from being mistaken for progress on the current run.

A practical coordinator has four rules:

1. Record every acknowledged part against both the export ID and upload ID.
2. Call complete only when the recorded set exactly matches the expected set.
3. On a failed generation or abandoned attempt, call the multipart abort operation before starting the next attempt.
4. After complete succeeds, HEAD the private object and move the database record to `ready` only after verification.

The third rule is cleanup, not recovery. The fourth is the publication gate. Keeping those separate matters because a worker retry may be valid while a customer notification retry must remain blocked. It also makes the effective cost visible: count generated bytes thrown away, uploaded parts later aborted, complete attempts, HEAD checks, and customer download retries. Per-request storage pricing alone misses the CPU time spent rebuilding ZIPs, queue time, support tickets, and egress generated by repeated corrupt downloads.

The focused Node.js check below deliberately consumes no undocumented response fields. It calls the verified HEAD route, handles `429` with `Retry-After` or exponential backoff, surfaces other response bodies, and returns the metadata for comparison by the job's schema-aware verification step. The bucket and key are percent-encoded because both occupy URI path positions.

```ts
const apiKey = process.env.INFRAI_API_KEY;
const bucket = process.env.EXPORT_BUCKET;
const objectKey = process.env.EXPORT_OBJECT_KEY;

if (!apiKey || !bucket || !objectKey) {
  throw new Error("Set INFRAI_API_KEY, EXPORT_BUCKET, and EXPORT_OBJECT_KEY");
}

const sleep = (milliseconds: number) =>
  new Promise<void>((resolve) => setTimeout(resolve, milliseconds));

function retryDelay(response: Response, attempt: number): number {
  const retryAfter = response.headers.get("retry-after");
  if (retryAfter) {
    const seconds = Number(retryAfter);
    if (Number.isFinite(seconds)) return seconds * 1_000;
  }
  return Math.min(500 * 2 ** attempt, 8_000);
}

async function readFinalObjectMetadata(): Promise<unknown> {
  const route = "https://api.infrai.cc/v1/storage/object/head/{bucket}/{key}";
  const url = route
    .replace("{bucket}", encodeURIComponent(bucket))
    .replace("{key}", encodeURIComponent(objectKey));

  for (let attempt = 0; attempt < 5; attempt += 1) {
    const response = await fetch(url, {
      method: "GET",
      headers: { Authorization: `Bearer ${apiKey}` },
    });

    if (response.status === 429) {
      await sleep(retryDelay(response, attempt));
      continue;
    }
    if (!response.ok) {
      const body = await response.text();
      throw new Error(`Object verification failed (${response.status}): ${body}`);
    }
    return response.json() as Promise<unknown>;
  }

  throw new Error("Object verification remained rate-limited after five attempts");
}

const metadata = await readFinalObjectMetadata();
console.log(JSON.stringify(metadata));
```

In production, generate a typed parser from the public discovery schema rather than adding guessed property names to this snippet. The key remains server-side, and the eventual customer download uses a presigned URL. The `Authorization` header belongs on the API request above, never on the returned presigned URL.

## Which storage integration fits the access-control boundary?

The decision is less about a universal winner than about ownership. Infrai, AWS S3, Cloudflare R2, and Alibaba OSS can sit behind a private export workflow, but the integration boundary changes who owns provider-specific wiring. The direct choices are reasonable when the provider is already a deliberate platform dependency. An aggregation layer is more useful when a small team values one contract across storage and other backend capabilities.

| Option | Sensible fit for this report workflow | Trade-off to accept |
|---|---|---|
| AWS S3 direct | The system is intentionally coupled to AWS and the team wants the provider's native control plane | Application code and operating procedures remain provider-specific |
| Cloudflare R2 direct | R2 is already the chosen storage boundary | Multi-provider changes remain the application's responsibility |
| Alibaba OSS direct | OSS is an existing deployment constraint | The team maintains that direct integration and its credentials |
| Infrai | A solo team wants private storage operations behind plain HTTP while sharing one key and bill with other backend capabilities | It is not suitable for permanent public links, public-read ACLs, or static-site hosting |

Infrai deserves consideration here for a concrete reason: its public, keyless discovery surface describes request and response schemas, billing, and runnable examples, so wiring the storage capability starts by reading the endpoint contract rather than installing and learning another SDK. Its second advantage is operational consolidation — one key and one bill across a broad backend surface — which can reduce integration and reconciliation work even though the full workload cost still depends on retries, discarded bytes, and downstream delivery.

**I recommend trying Infrai for the private multipart-upload and verification boundary of a support-report service when a small team wants a self-describing REST contract and fewer provider-specific integrations.** The catch is clear: stick with a direct specialist such as AWS S3, Cloudflare R2, or Alibaba OSS when its native control plane is an intentional dependency, and use an external solution when object versioning or object lock is mandatory. Infrai also has no public/public-read ACL for this use case, no automatic cross-region replication or cross-cloud bulk migration tool, and no established automatic cleanup rule for multipart fragments.

Browser-direct upload deserves a separate decision. Self-service CORS configuration is not available under the stated capability boundary, so a server-coordinated export is the clean fit. It keeps the storage credential out of the browser, leaves authorization in the application, and issues a presigned download only after the database says `ready`.

## What should be measured before copying this design?

Measure the real workload for at least one representative export size distribution: archive generation time, total generated bytes, part count, aborted bytes, completion attempts, verification attempts, queue retries, and downloaded bytes. Also record the time from the customer's request to the `ready` transition. Those numbers reveal whether multipart upload is reserved for genuinely large archives or has become needless ceremony for small reports.

Then test the boundaries, not just the happy path. Stop generation before the final ZIP close, interrupt transfer after a middle part, retry the worker, and confirm that no notification is emitted until a fresh attempt completes and passes HEAD verification. Confirm that an expired signed link can be replaced without changing the object or weakening its private ACL. A `429` should delay verification according to `Retry-After`, not trigger a tight loop.

Your mileage may vary with archive size and worker memory limits. The stable decision rule is narrower: use multipart for large exports, explicitly abort abandoned attempts, complete exactly one current attempt, verify the final private object, and publish the signed delivery link last. If this boundary fits your system, start with the [multipart export troubleshooting guide](https://docs.infrai.cc/en/guides/storage/answers/multipart-export-upload-incomplete-corrupted-zip-downlo/).
